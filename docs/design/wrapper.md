# Wrapper design

The wrapper is the execution boundary between Bazel actions and the configured Pyrefly executable.
The aspect registers a check, stubgen, or minify action, and the wrapper turns the action's declared
inputs into the corresponding check, generated-stub, or filtered-source result.

## Role in Bazel actions

All action types use the same wrapper target. The wrapper:

- Resolves the toolchain executable for check and stubgen from its execroot-relative path after the
  spawn starts.
- Accepts Bazel parameter files so large source and import graphs do not exceed command-line limits.
- Runs the configured Pyrefly binary for check and stubgen actions.
- Classifies type errors, expected failures, timeouts, and infrastructure failures into Bazel action
  results.
- Emits diagnostics and wrapper logs without changing Pyrefly's consumer-owned diagnostics policy.

Resolving the executable inside the spawn keeps action keys independent of a user's output base and
of machine-specific sandbox paths. The same action shape works for local, sandboxed, and remote
spawn strategies.

## Check actions

For a check action, the wrapper builds an effective temporary `pyrefly.toml` and invokes
`pyrefly check`. It preserves consumer-owned policy while replacing settings that Bazel must
control, including:

- Source files and project includes.
- Import and site-package search paths.
- Generated and configured stub paths.
- Python platform and version values derived from the configured Bazel target.
- Interpreter-query behavior.

The effective paths reconstruct the import environment declared by the target's Bazel dependency
graph. Roots containing the target's direct source files are placed in `search-path`; first-party
checks also retain the main repository root so repository-qualified imports remain available
alongside explicit `PyInfo.imports` roots. Stubgen does the same when generating interfaces for a
main-repository target. The wrapper resolves each direct source set once into declared and effective
roots. Matching roots are excluded from `site-package-path`. Dependency imports in
`site-package-path` use the following precedence:

1. Stubs explicitly mapped to a runtime package.
2. `.pyi` files bundled with the runtime distribution.
3. Stubs generated by upstream stubgen actions.
4. Minified runtime Python sources for dependencies that were not replaced by mapped or generated
   stubs.

Dependency import roots are resolved across the complete graph by Bazel layout tier: generated roots
precede source roots. The wrapper first records the resolved standard-library, mapped, bundled,
generated, and retained runtime roots as an ordered import-view plan. It then materialises that plan
as one site-package directory and supplies the resulting path to configuration construction. This
avoids Pyrefly linearly searching hundreds of dependency-specific paths for every import without
changing the identity of the direct files being checked.

Mapped, automatically stubbed, and minified dependencies do not also contribute their original file
sets to downstream actions. TreeArtifacts are passed between actions as unexpanded directory roots.
Each dependency artifact already contains the representation selected by its own stubgen or minify
action. The wrapper discovers bundled `.pyi` files only in the direct target inputs, where they must
precede newly generated interfaces.

Before launching Pyrefly, the wrapper applies the configured `project-excludes` globs to the
action's direct sources. If every source is excluded, the check is a no-op and the wrapper creates
the validation marker without resolving or invoking the Pyrefly executable.

Expected failures are a strict ratchet:

| Pyrefly result                  | Expected failure | Bazel action                                      |
| ------------------------------- | ---------------- | ------------------------------------------------- |
| Clean                           | No               | Succeeds and creates the validation marker        |
| Type errors                     | No               | Fails                                             |
| Type errors                     | Yes              | Succeeds and creates the validation marker        |
| Clean                           | Yes              | Fails because the expected-failure entry is stale |
| Infrastructure error or timeout | Either           | Fails                                             |

Missing executables, wrapper failures, Pyrefly subprocess timeouts, and Pyrefly infrastructure exit
status `3` are always infrastructure failures.

## Baseline-update actions

The baseline-update subcommand shares check preprocessing and configuration construction, but
removes any inherited baseline and points Pyrefly at a fresh declared output. It invokes `check`
with `--update-baseline` and accepts exit status `1` because type errors are the content being
recorded rather than an action failure. Expected-failure inversion does not apply.

If configuration excludes every direct source, the wrapper writes an empty baseline so the action
still fulfills its single declared output. The executable baseline registry interprets that output
as a request to remove any checked-in baseline for the target.

## Stubgen actions

For a stubgen action, the wrapper prepares a compact importable output tree from the selected
dependency:

- Builds the same effective Bazel-owned Pyrefly configuration as a check action and preserves the
  same consumer-owned policy.
- Existing `.pyi` files and `py.typed` markers are preserved.
- Native extension modules receive importable shim stubs.
- Generated files, preserved stubs, and native shims are stored once at their repository-relative
  paths. This layout is identical for main-repository and external targets.
- Pyrefly stubgen runs for uncovered Python source files.
- Explicitly mapped stubs are copied into the output and supplied as context during generation. A
  PEP 561 `partial` marker permits generation for uncovered runtime modules; without it, runtime
  interfaces are omitted.
- Dependencies of the mapped stub target remain separate import roots. They inform generation and
  propagate downstream without participating in direct mapped-package coverage.
- Roots containing those direct Python files are supplied through `search-path`, while the merged
  `site-package-path` contains only inputs which inform their analysis.
- Private-name and docstring emission follow the action's explicit settings.
- Dependency imports use the same mapped, bundled, generated, then retained source precedence as
  check actions.
- Outputs of upstream automatic stubgen and minify actions are available while generating stubs for
  downstream targets.

Every Pyrefly invocation within one stubgen action reuses that effective configuration. Search-path
heuristics and interpreter queries therefore cannot make stub generation depend on the execution
environment.

## Target Python environment

Check and stubgen actions receive their Python version from the active rules_python target runtime
toolchain. A `py_binary` or `py_test` transition therefore also configures the environment used to
check each `py_library` in its dependency graph. A library built directly uses the invocation's
default Python target configuration.

The Python platform comes from the target platform's operating-system constraint. The ruleset maps
the corresponding `@platforms` constraints to Python's known `sys.platform` values for Android,
Emscripten, FreeBSD, iOS, Linux, macOS, Windows, and WASI. AIX and Cygwin have no distinct
`@platforms` constraint. Neither the platform nor version is inferred from the wrapper interpreter
or the execution platform.

Bundled stubs discovered in the target's input tree are copied into the final output after
generation, so a generated stub cannot replace a sibling `.pyi` shipped by the distribution.

Each transformed TreeArtifact describes its internal import roots. For a main-repository target
these include the artifact root and every explicit `PyInfo.imports` root. For an external target
they include its explicit import roots. Its artifact root is additionally exposed when
rules_python's `experimental_python_import_all_repositories` build setting is enabled. Downstream
check and stubgen actions expand those roots without duplicating files inside the artifact. Mapped
stubs occupy a separate, highest-precedence internal root.

Each Pyrefly invocation within stubgen uses a size-adjusted subprocess timeout. Exceeding it fails
the action.

Package selection remains an analysis-phase responsibility. The wrapper receives only targets for
which the aspect or the public `pyrefly_stubs` rule registered a stubgen action.

## Minify actions

A minify action is the non-inference alternative to stubgen. It materializes a compact import tree
without launching Pyrefly:

- Python source files, notebooks, bundled `.pyi` files, and `py.typed` markers are copied to
  repository-relative paths.
- Native extension binaries are replaced by empty importable `.pyi` shims.
- Data files, metadata, shared libraries, and other files which cannot inform static type checking
  are omitted.

The aspect registers `PyreflyMinify` for targets that do not receive `PyreflyStubgen`. If the target
has mapped stubs, minification copies them and retains runtime interfaces only for gaps declared by
a partial stub package. Downstream check and stubgen actions consume the minified TreeArtifact
rather than the target's original file set. A configured exclusion tag suppresses checking only; the
target still receives stubgen or minify so it remains usable as a dependency.

## Logging and runtime requirements

`--@pyrefly.bzl//pyrefly:log_level=<level>` controls wrapper logging for Bazel actions. Direct
wrapper invocations can additionally supply a log file. Failures include tracebacks when wrapper
infrastructure itself raises an exception.

Each wrapper subcommand records a root OpenTelemetry span plus nested spans for its internal phases
and subprocess calls in a declared OTLP/JSON Lines output. Spans include work-unit counts where
relevant, and subprocess spans include their timeout and exit code. The aspect exposes traces from
wrapper actions created directly for the target through the `pyrefly_otlp_traces` output group.

The wrapper requires Python 3.11 or newer. It does not import Pyrefly as a Python package; the
configured executable is always invoked as a separate process.

The wrapper will likely be superseded in the future by the `pyrefly bazel-check` command.
